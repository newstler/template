# Upgrading apps forked from this template

## RubyLLM 1.x → 2.0

For apps on ruby_llm 1.9–1.16 whose schema came from this template (the `models`, `chats`, `messages` and `tool_calls` tables, including the `upgrade_to_v1_14` columns). You don't need to deploy 1.16 first: the committed migrations take a 1.x database straight to 2.0 in one `db:migrate`.

### Steps

```bash
git checkout -b ruby-llm-2
git fetch template && git merge template/main
bundle install

# Back up first — the migrations are irreversible.
cp storage/development.sqlite3 storage/development.pre-ruby-llm-2.sqlite3
# Production: confirm a fresh Litestream snapshot before deploying.

bin/rails ruby_llm:upgrade_check   # fix every [blocker]; read every [review]
bin/rails db:migrate
bin/rails ruby_llm:upgrade_check   # expect "nothing to fix."
bin/ci
```

`ruby_llm:upgrade_check` is read-only. It scans `app/`, `lib/` and `config/` for 1.x APIs that 2.0 removed and prints each hit with its replacement. Before migrating, it also checks for data the upgrade migrations refuse to migrate. It exits non-zero while blockers remain.

### What the migrations do

1. `PrepareRubyLlmV2Data` (template): renames `messages.cost` to `total_cost` so historical costs carry over, and rewrites `messages.model_id` from a `models.id` UUID to the model name. It gives chats without a model the `Setting.default_model` model; if that's unset or not in the registry, it uses the chats' most-used model. It stops before changing anything if the `models` table is empty (run `bin/rails ruby_llm:load_models` on the 1.x release first).
2. `PrepareRubyLlmV2Upgrade` / `BackfillRubyLlmV2Data` / `FinishRubyLlmV2Upgrade` (generated by `rails g ruby_llm:upgrade`, rename mode):
   - rename `models` → `ruby_llm_models` and `tool_calls` → `ruby_llm_tool_calls`
   - move chats to `ruby_llm_model_id`
   - copy message tokens and cost into `ruby_llm_usages`
   - link each tool result to its call
   - The template patches the generated migrations so `ruby_llm_usages` and `ruby_llm_batches` get `uuid7()` ids.
3. `CleanupRubyLlmV2Upgrade` (generated) drops the legacy message columns (`model_id`, `tool_call_id`, `content_raw`, token and cost columns).
4. `DropAppCostCaches` (template) drops `chats.total_cost`, `users.total_cost` and `ruby_llm_models.chats_count` / `total_cost`, plus the `chat` rows in `ai_costs` whose message still exists (their cost now lives in `ruby_llm_usages`). Rows for chats deleted before the upgrade stay, so dashboard totals don't drop. From now on, deleting a chat also deletes its usage rows and its spend.

All of them are irreversible: to roll back, restore the backup and the previous release. If you want upstream's safety window between the upgrade and the column cleanup, leave `*_cleanup_ruby_llm_v2_upgrade.rb` and `*_drop_app_cost_caches.rb` out of your merge and ship them in a later release.

Extra columns your app added to `chats` or `messages` are kept. Extra columns on `models` are kept too, but `RubyLLM.models.refresh` doesn't write them.

### Code changes

| 1.x | 2.0 |
|-----|-----|
| `Model` (app class), `acts_as_model` | `RubyLLM::ActiveRecord::Model`; the template adds `.enabled`, `.embedding` and `.with_usage_cost` |
| `ToolCall` (app class), `acts_as_tool_call` | `RubyLLM::ActiveRecord::ToolCall`; `message.tool_calls` is a Hash of `RubyLLM::ToolCall` (`each_value`) |
| `acts_as_chat messages_foreign_key:` / `acts_as_message tool_calls_foreign_key:` | `acts_as_chat` / `acts_as_message` |
| `belongs_to :model` on `Chat` | remove it; `acts_as_chat` defines it (FK `ruby_llm_model_id`) |
| `Model.refresh!` | `RubyLLM.models.refresh` |
| `RubyLLM::Models.find(id)` / `models.find(id, :openai)` | `RubyLLM.models.find(id, provider: :openai)` |
| `with_params(...)` | `with_provider_options(...)` |
| `response_format: { type: "json_object" }` | OpenAI now uses the Responses API: `with_provider_options(text: { format: { type: "json_object" } })`, or `config.openai_protocol = :chat_completions` |
| `on_new_message` / `on_end_message` | `before_message` / `after_message` |
| `on_tool_call` / `on_tool_result` | `before_tool_call` / `after_tool_result` |
| `with_tool(T)` | `with_tools(T)` |
| `response.input_tokens` / `output_tokens` | `response.tokens.input` / `.output` |
| `message.input_tokens`, `message.cost` (decimal) | `message.tokens.input`, `message.cost.total` |
| `chat.total_cost`, `user.total_cost` | `chat.cost.total`, or `Chat/User/Team.with_usage_cost` → `usage_cost` |
| `message.model_id` | `message.model` (String) |
| `RubyLLM::Tokens.build` | `RubyLLM::Tokens.new` |
| `RubyLLM::Schema` | `Schematist::Schema` |
| Tool `desc` / `param` / `desc:` | `description` / `parameter` / `description:` |
| `model.supports_vision?`, `input_price_per_million` | `model.supports?(:vision)`, `model.price(:input)` |
| Standalone call cost (`AiCost.record!`) | `AiCost.record_response!(cost_type:, model_id:, response:)` |

Full upstream guide: https://rubyllm.com/next/upgrading/

### Later

The generated migrations `require` generator code from the ruby_llm gem. Build new environments with `bin/rails db:prepare` (schema load) instead of replaying every migration, so a future 2.x that reorganises those internals doesn't matter.
